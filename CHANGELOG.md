- 2026-06-13 11:03:47 +0700 - Fix Brain View Empty Boot Root Cause
  - Status: Uncommitted
  - Areas changed: dashboard state hydration (`src/lib/services/dashboard-state-client.ts`, `scripts/test-dashboard-state-snapshot.mjs`), Brain graph API/native builders (`src/lib/services/obsidian/brain-graph.ts`, `src-tauri/src/brain.rs`), Brain graph refresh and inspector UI (`src/features/dashboard/hooks/use-miroshark-brain-controller.tsx`, `src/features/dashboard/views/BrainGraphExplorer.tsx`)
  - Summary: Fixes the Brain view empty-boot root cause: an expired or missing dashboard auth session could make `/api/dashboard/state` return `401`, and the client treated that auth denial as a legitimate empty dashboard snapshot. That let an already-mounted dashboard hydrate into a fake-empty Brain state with 0 notes instead of returning to the unlock flow. The snapshot loader now treats auth denial as auth denial, never `{}`, and a regression test locks that behavior. As secondary guardrails, the Brain graph loader refuses to accept an empty native graph without trying the API graph builder, both graph builders now emit one edge per source/target pair, the inspector dedupes linked-node lists before rendering buttons, and the native scanner reports folder read failures instead of silently turning them into an empty graph.
  - Verification: `pnpm test:dashboard-state-snapshot` passed; `cargo check` passed for the Tauri native scanner; `pnpm exec eslint src/lib/services/dashboard-state-client.ts src/lib/services/obsidian/brain-graph.ts src/features/dashboard/views/BrainGraphExplorer.tsx src/features/dashboard/hooks/use-miroshark-brain-controller.tsx` reports no errors, only pre-existing hook dependency warnings in the large controller; live `localhost:5121` checks show `/api/dashboard/state` returns `401` when unauthenticated while `/api/obsidian/graph` can still return the populated vault graph (`267` nodes and `11` deduped links, no duplicate edge pairs), confirming the graph endpoint was not the empty-boot root failure and the duplicate React key warning path is removed. Full `pnpm typecheck` is blocked by an unrelated existing Remotion error in `remotion/gitlawb-integration-video/src/GitLawbIntegrationVideo.tsx` (`pathLength` is not a valid CSS property).

## 2026-06-13 10:52:28 +0700 - Fix Stuck Dashboard Loading Screen And Add Issue Reporting

- Status: Pushed
- Areas changed: dashboard hydration loader (`src/lib/services/dashboard-state-client.ts`, `src/features/dashboard/DashboardApp.tsx`), new client issue reporter (`src/lib/utils/issue-reporter.ts`), new Cloudflare Worker (`workers/issues/`)
- Summary: Fixes the bug where a fresh install could sit forever on a loading screen ("Scanning fleet discovery" on the desktop, "Opening Agent Chat" on mobile). Both screens gate on dashboard hydration, which only completed after the local-state snapshot loaded — and that loader retried `/api/dashboard/state` indefinitely with no give-up, so any persistent backend failure left the app on an endless spinner. The retry is preserved (it protects stored chat history from an empty-boot overwrite), but after ~10s of failure the app now shows a recoverable "Still connecting to HivemindOS…" screen with a Reload button that clears itself the moment the service answers. Broken boots are also reported (anonymized: failure kind, HTTP status, app version, coarse UA, random per-install id — never user content, paths, secrets, or IPs) to a new `hivemindos-issues` Cloudflare Worker + D1, so a stuck install is visible centrally without asking the user to open devtools.
- Verification: `tsc`/`eslint` clean on all changed files; `pnpm test:dashboard-state-snapshot` green (no-data-loss semantics preserved); issues Worker deployed and round-trip verified live (POST accepted, token-gated read works, unauthorized → 401). The loading screen itself is Tauri-only and needs a desktop build for a live look.
- Intended commit message: `Fix dashboard loading-screen hang; add anonymized issue reporting`
