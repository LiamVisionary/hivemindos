Shared Brain Memory Benchmarks

These benchmarks measure how well HivemindOS’s shared brain recalls the right memory, how fast it does it, and how much less text it sends to models. Latest results: September 25, 2026.

LongMemEval Oracle Against Sibyl-Memory

Sibyl-Memory publishes a 95.6% score on LongMemEval Oracle: 500 questions, each given the past conversations that hold its answer. We ran the same 500 questions through the Superbrain the way an agent asks it (hive-brain answer), with Claude reading the answer from what the Superbrain returned.

  • Questions: all 500 of longmemeval_oracle.json from the cleaned LongMemEval release. Each question’s conversations go into a fresh, empty Superbrain, and the question is asked with its own date as today.
  • Readers: Opus 4.6 (the model behind Sibyl-Memory’s headline) and Sonnet 4.5 (the model of its plugin run). LongMemEval’s official reading prompt, unchanged; temperature 0; no extended thinking.
  • Judge: LongMemEval’s official per-type judge prompts with gpt-4o-2024-08-06, for every answer, ours and Sibyl-Memory’s.
  • Sibyl-Memory: its published answer files from Sibyl-Labs/memory-bench-kit, graded by the same judge. We did not re-run its system.
  • Headline: excludes the 30 preference questions, as Sibyl-Memory’s does. Both figures are shown.
System Reading model Correct, excluding preference (470) Including preference (500)
HivemindOS Superbrain Claude Opus 4.6 454 (96.6%) 483 (96.6%)
Sibyl-Memory Claude Opus 4.6 448 (95.3%) 475 (95.0%)
HivemindOS Superbrain Claude Sonnet 4.5 447 (95.1%) 473 (94.6%)
Sibyl-Memory plugin Claude Sonnet 4.5 436 (92.8%) 461 (92.2%)
Sibyl-Memory Claude Sonnet 4.6 430 (91.5%) 452 (90.4%)
Question type HivemindOS (Opus 4.6) Sibyl-Memory (Opus 4.6) HivemindOS (Sonnet 4.5) Sibyl-Memory plugin (Sonnet 4.5)
User facts (70) 70 70 69 68
What the assistant said (56) 56 56 56 56
Updated facts (78) 76 72 77 72
Counting across chats (133) 123 124 117 114
Dates and time (133) 129 126 128 126
Preferences (30) 29 27 26 25

What this shows:

  • With the same reading model, HivemindOS scores higher. With Opus 4.6, on the same 470 questions, it answered 16 that Sibyl-Memory missed, and Sibyl-Memory answered 10 that it missed (exact McNemar test, p = 0.33). With Sonnet 4.5 the counts were 21 and 10 (p = 0.07).
  • Ahead, but not proven beyond chance. Six questions out of 470 is within what a second run of either system could change. Updated facts and dates carry most of the lead; Sibyl-Memory’s Opus run counts across conversations slightly better.
  • What moved the score. The first full HivemindOS run scored 91.1% with Sonnet 4.5. Four changes took it to 95.1%: finding conversations by the days a question names (“two weeks ago”) even when no word matches; labeling each session with how long before today it was; handing over whole conversations when they fit; and no longer repeating an excerpt above its full text.

Limitations. The changes were found by studying misses on these same 500 questions, with no separate held-out set (see the LoCoMo held-out test). They are general product behavior, not per-question rules, and shipped for every user. There was one run per configuration. Every full run is in the receipt: Sonnet 4.5 first version 91.1%, reported 95.1%, with the optional conversation ledgers 94.5%; Opus 4.6 reported 96.6%, with ledgers 96.0%. Sibyl-Memory’s own 95.6% comes from a string-matching scorer that accepts almost any step-by-step answer containing the right number; graded by the official judge, its Opus run scores 95.3%. Oracle gives each question only the conversations that hold its answer, so it tests reading and recall, not search through a large history.

The published receipt holds the exact text the Superbrain gave the reading model for every question, every answer, and every verdict. Two free checks need only the public dataset: one confirms every piece of conversation text the model saw comes word for word from that question’s own history, and one recomputes every number above. Scripts to re-grade or re-read on your own API key are included.

LongMemEval_S Against Sibyl-Memory’s Architecture

LongMemEval_S asks the same 500 questions but buries each answer among about 50 conversations (about 490,000 characters), which is the real job of a memory system. Sibyl-Memory has published no S result, so we ran its published architecture with its public runner: Claude Code reads the question’s whole chronological journal under Sibyl-Memory’s instructions. Its plugin product was not run, because the integration behind it is shared only with beta testers.

  • Both sides: Claude Opus 4.6 reading; LongMemEval’s official judge prompts with gpt-4o-2024-08-06.
  • Sibyl-Memory: its runner unchanged except the per-question time limit (120 s to 600 s, because S journals are about ten times longer than Oracle’s), run with an empty home directory so no local settings reached it. The plan was published before it answered anything.
  • HivemindOS: hive-brain answer as it ships, without model ordering or embeddings.
  HivemindOS Sibyl-Memory (architecture)
Excluding preference (470) 443 (94.3%) 433 (92.1%)
All 500 470 (94.0%) 457 (91.4%)
Updated facts (78) 74 70
Counting across chats (133) 116 118
Dates and time (133) 127 121
Tokens the reading model read, per question 12,096 111,675

HivemindOS answered 26 questions Sibyl-Memory missed, and Sibyl-Memory 16 that HivemindOS missed (p = 0.16): higher, not established beyond chance, while giving the model about a ninth of the text. Deviations are disclosed with the receipt: two copies of the run overlapped and answered 200 questions twice (the first answer counts), and requests refused for lack of API credit were re-sent.

LoCoMo held-out test

To check that the LongMemEval changes didn’t just fit LongMemEval’s questions, we pre-registered a comparison on LoCoMo, which none of them was developed on: 500 sampled questions, memory code from before the LongMemEval work against the code after it, Claude Opus 4.6 reading, Mem0’s published LoCoMo prompts and judge.

Code Correct
Before (the 91.1% LongMemEval version) 467 (93.4%)
After (current) 472 (94.4%)

The newer code answered 13 questions the older missed and missed 8 it answered (p = 0.38). The changes did not overfit LongMemEval, and they are not shown to help on LoCoMo. The newer code gives the model about twice as much text there. A second pre-registered variant (both speakers stored as the user) produced empty memory, because saved conversations need an assistant turn; it is published as a failed run. Receipt.

Public long-conversation suites

HivemindOS also runs the full public LoCoMo, LongMemEval, and BEAM suites through the product’s own conversation archive, vault index, and recall ranking. These are complete Top-50 retrieval runs, not hand-picked samples.

Public suite Full questions Retrieval-quality result Local p50 / p95
LoCoMo 1,540 99.93% Top-50 evidence-session recall; 93.95% Top-10 6.4ms / 14.72ms
LongMemEval 500 99.4% Top-50 evidence-session recall; 97.6% Top-10 101.8ms / 285.76ms
BEAM 1M 700 700/700 returned context; 10 median hits 121.9ms / 583.2ms
BEAM 10M 200 200/200 returned context; 50 median hits 1,053.5ms / 3,829.7ms

Evidence-session recall asks whether the labeled source conversation was among the retrieved memories. It measures retrieval, not final-answer accuracy. BEAM has no equivalent labels in this adapter, so its rows show only that context came back, not that every result was relevant.

Across the 2,036 eligible LoCoMo and LongMemEval questions, HivemindOS retrieved the labeled source session for 1,931 at Top-10 (94.84%) and 2,032 at Top-50 (99.80%).

Recall on messy questions

The 1,000-query live memory matrix didn’t only search exact titles. It also used sparse terms, conversational noise, typos, natural phrasing, and type, project, and tag filters.

Query form Top-1 Top-3 Cases
Exact title, automatic time mode 100% 100% 103
Exact title, current mode 100% 100% 103
Sparse title terms 83% 99% 103
Noisy natural question 86% 99% 103
Typo query 81% 91% 103
Natural memory-type intent 83% 99% 103
Type-filtered 94% 99% 103
Project-filtered 93% 99% 103
Tag-filtered 92% 98% 102

Overall: 90% Top-1, 98% Top-3, and 0.94 MRR. Typos are the main weakness: 91% Top-3 but 81% Top-1.

The same run also checked:

  • Abstention: unrelated compound questions returned no memory in 10/10 cases.
  • Receipt isolation: 40/40 checks passed. Old operational receipts stayed out of normal recall but could still be requested.
  • Time: current, historical, and as-of questions reached 96% Top-1 and 100% Top-3.

The 1,000 calls ran at 86.38 sequential queries per second, with 12.27ms p50 and 16.28ms p95 latency.

Hosted SuperAgent API memory

Cloud Superbrain was tested through the public SuperAgent API on August 27, 2026. Three fresh accounts each got the same memory corpus and were measured three times after warmup.

Hosted path Quality result in every trial Median of trial p50s Trial p50 range
Lexical search 8/8 behavior cases 534.48ms 448.99–663.90ms
Hybrid semantic recall 6/6 Top-1 cases 4,894.42ms 4,514.84–4,921.65ms
Grounded answer 3/3 cases 5,931.26ms 5,290.64–6,245.85ms

Matching local runs also passed 8/8 and 6/6, with a median trial p50 of 7.85ms and p95 of 11.63ms. Hosted recall matched local quality on this corpus, but not local speed.

A separate test added 48 misleading archive memories that reused the same terms (57 hosted memories, 55 local; the hosted test carried two extra knowledge nodes for answer grading). Every case stayed correct. The single hosted run measured 431.67ms lexical p50, 1,674.67ms semantic p50, and 2,594.36ms answer p50; the matching local lexical run measured 14.48ms p50. This shows the distractors didn’t push out the right memories; it is not a full scale or speed comparison.

These cases don’t use a private vault and don’t prove equal recall on any data. Hosted timings include internet transit, account isolation, metering, storage, and any paid semantic or answer work.

Past conversations on LongMemEval_S

On September 23, 2026, hosted memory gained the shared brain’s recall of past conversations: the best-matching exchanges under each conversation’s date, ordered by the Turbo decision model for Memory Answer. It was measured before and after on LongMemEval_S through the hosted search, recall, and answer code, with each question’s 50 or so chats saved to a fresh account and semantic recall off.

Hosted result Before After
Memory Answer’s reader received every piece of evidence, keyword order (470 answerable questions) 9.6% 85.1%
Recall’s 4,200-character conversationEvidence held every piece of evidence not available 56.4%
Every evidence conversation was among the top 50 search results 82.3% 98.5%
Memory Answer was correct (150 questions, 25 of each type) 16.7% 81.9%
  • The new Memory Answer was right on 98 questions the old one missed, and the old one on 1.
  • Retrieval and reader both mattered. With the old answer model, the new recall alone lifted correct answers from 16.7% to 45.3%; that small model often said it had no information. Memory Answer now uses a larger model at the same price per token, which reached 81.9%. It reasons before answering, adding about three seconds to the reader’s median time.
  • The decision model helped in less space. Ordered by it, the evidence fit in 12,000 characters for 81.1% of questions, against 74.8% in keyword order, and the reader did better with those 12,000 characters than with 24,000 in keyword order.

Limitations. Answers were graded with LongMemEval’s official judge instructions but by gpt-4o-mini instead of gpt-4o, so compare these rows with each other, not with the head-to-head above. With semantic recall on, as in paid plans, recall can only gain candidates. LongMemEval measures memory of past conversations; typed memories are covered by the hosted cases above.

Searching the whole vault

Typed memory is the fast path for facts, preferences, and decisions. When that isn’t enough, HivemindOS searches your normal vault notes through an index and loads only the best matches. The eight-case live benchmark covered project decisions, policies, docs, skills, secure references, imported sources, and intake notes.

Full-vault path Top-1 / Top-3 / MRR Median latency
Previous file-search path 1.00 / 1.00 / 1.00 745.04ms
Direct lexical index 1.00 / 1.00 / 1.00 48.42ms
Final tiered runtime 1.00 / 1.00 / 1.00 300.33ms

The index was 15.39× faster with the same first result in every case. The full runtime is slower because it also routes, loads, and ranks the final results.

A larger test indexed 25,995 eligible notes from a 28,549-file vault in about 9.2 seconds, producing a 70.6 MB local index. Across five queries, median search dropped from 2,285ms to 118ms (19.4×) with identical Top-1 results.

Fewer tokens

Memory saves money only when agents load focused context instead of whole files and histories. The live token benchmark sent the same task to the same model twice: once with a broad context pack and once with a targeted Hive pack.

Live provider scenario Baseline total tokens Hive total tokens Total reduction
Focused shared-brain recall 43,754 370 99.2%
Complex dashboard chatbot build 42,571 5,307 87.5%

These are provider-reported counts from live OpenRouter calls with openai/gpt-4.1-mini. The broad pack was cut off at 180,000 characters in both runs; the Hive packs were not. They measure context size, not an invoice or answer quality. Full prompts and method are in Token And Cost Savings.

A local estimate over four scenarios (brain recall, software build, chatbot build, workflow reuse) counted 2,906,702 baseline context tokens against 22,764 targeted Hive tokens, a 99.2% reduction. It is a text-size estimate, not provider billing.

Cleaner current truth

Two design choices keep memory clean:

  1. Routine receipts, retries, and completions go to a separate operations journal, not long-term memory.
  2. Each durable memory has one current version; reviewed updates keep older versions as history.
Health signal Before separation and reviewed cleanup Current
Near-duplicate groups 5 0
Largest duplicate cluster 44 receipts 0
Canonical conflict groups 3 0
Active records affected by canonical conflicts 9 0

The current snapshot has 101 active memories and 21 older versions kept as history. Forty-seven old operational records are still available on request but no longer appear in normal recall. This combines the design change with a reviewed cleanup, so it isn’t an automatic cleanup rate for every vault.

Pattern mining, with a gate

Pattern mining suggests new memories, skills, or routines from repeated events, so noise must not become advice. The labeled 47-event test set has three real patterns and many traps (retries, test runs, one-offs, unknown outcomes). The miner returned exactly the three real ones:

Pattern metric Result Enablement gate
Precision 1.00 0.90
Recall 1.00 0.80

This passes the test gate but isn’t production precision. Pattern mining stays a dry run by default and only creates proposals for you to review. Automatic promotion stays off until there is enough real reviewed evidence.

Quoting these results

  • Quote the Sibyl-Memory comparisons with their setup: LongMemEval Oracle (or LongMemEval_S), all 500 questions, the same reading model on both sides, the official gpt-4o-2024-08-06 judge for both, and Sibyl-Memory’s own published answers (or, for S, its published architecture run by us with its public runner).
  • Say HivemindOS scored higher. Don’t say the difference is statistically significant: it isn’t (p = 0.33 with Opus 4.6 on Oracle, p = 0.16 on S).
  • The LongMemEval_S result is not a comparison with Sibyl-Memory’s plugin product.
  • Don’t turn these results into an unmeasured competitor comparison, a hosted speed guarantee, a universal token-savings promise, or a claim that pattern proposals are production-perfect.

Reproduce the benchmarks

The local and fixture benchmarks don’t need a paid model:

pnpm benchmark:agent-memory-live-recall -- --vault <vault> --calls 1000
pnpm benchmark:agent-memory-scale -- --calls 200
pnpm benchmark:agent-memory-upgrade -- --base-url <dashboard-url> --iterations 50 --warmup 2
pnpm benchmark:shared-brain-search -- --vault <vault> --limit 8
pnpm benchmark:agent-memory-pattern-mining
pnpm benchmark:context-savings

The API benchmark needs a running HivemindOS dashboard. The full-vault and live-memory benchmarks are read-only. The scale, API, and pattern benchmarks use isolated test data. The public-suite harness is development-only; datasets and raw outputs are not shipped with the app.

The LongMemEval Oracle comparison uses the public longmemeval_oracle.json from the LongMemEval Hugging Face dataset. Building each question’s Superbrain needs no model; the reader and judge call OpenRouter and cost about $20 for all 500 questions:

OPENROUTER_API_KEY=<key> node scripts/benchmark-longmemeval-arms.mjs retrieve --dataset <longmemeval_oracle.json> --out <dir> --arms product-answer-jev
OPENROUTER_API_KEY=<key> node scripts/benchmark-longmemeval-arms.mjs answer --out <dir> --arms product-answer-jev --reader anthropic/claude-sonnet-4.5 --judge openai/gpt-4o-2024-08-06 --reader-max-tokens 1500 --budget-usd 25
node scripts/benchmark-longmemeval-arms.mjs summarize --out <dir>

The published answers and a script that recomputes the scores are in hivemindos-memory-benchmarks.

The live token benchmark calls your chosen provider and may cost money:

./scripts/hive-env-run -- pnpm benchmark:e2e-token-savings -- --scenario brain-recall
./scripts/hive-env-run -- pnpm benchmark:e2e-token-savings -- --scenario chatbot-build
