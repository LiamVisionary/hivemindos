# Optimizations

This file records performance and latency optimizations that future agents should
reuse before re-debugging the same paths. Keep entries concrete: what was slow,
what changed, which files own the behavior, how it was verified, and what to
watch next.

This complements `CHANGELOG.md`. The changelog is release-facing; this file is
the engineering memory for optimization decisions and performance traps.

## Rules For New Entries

- Add an entry whenever you add, remove, or materially change a performance optimization, cache, timeout, debounce, polling rule, lazy load, prompt-size reduction, or expensive-work deferral.
- Record the measured bottleneck or failure mode, not just the code change.
- Include exact files or areas changed.
- Include verification commands and live timing evidence when available.
- Note tradeoffs, cache freshness, fallback behavior, and when the optimization should be revisited.
- If an optimization affects prompt injection or agent context, state what context is preserved and what is skipped, cached, compacted, or deferred.

## 2026-07-17 17:10 EDT (-0400) - Cache The Git-Free Latest-Commit Probe (Including Failures)

- Problem: Git-free archive checkouts (Windows fleet machines, desktop-app `app-source`) have no `git ls-remote` path to learn the latest main commit, so the collector's /health version payload now probes GitHub's commits API. /health forces a version refresh on every collector `/update`, and the version cache defaults to 60s (`AGENT_TELEMETRY_VERSION_CACHE_MS`) — an uncached probe could hit GitHub's unauthenticated limit of 60 requests/hour/IP, and an offline box would add a network timeout to every version refresh.
- Change: `fetchLatestMainCommit` in `scripts/lib/collector-source-version.mjs` caches the probed SHA for 10 minutes, and caches *failures* for the same window so offline or rate-limited boxes back off instead of retrying every refresh. The probe uses `Accept: application/vnd.github.sha` (bare-SHA text response, no JSON) with an 8s timeout. Git checkouts never hit this path.
- Tradeoffs: A stale cache window means a just-pushed commit can take up to 10 minutes to show as "update available" on git-free machines (git machines keep ls-remote freshness). A cached failure makes `latestCommit` fall back to the current commit — the machine reports "up to date" during an outage, which matches the existing `git ls-remote`-failure behavior on unix.
- Files: `scripts/lib/collector-source-version.mjs`, wired via `readCollectorAppVersion` from `scripts/agent-telemetry-collector.mjs`.
- Verification: `node scripts/test-collector-windows-update.mjs` covers cache hits, expiry, failure caching, and non-SHA rejection with an injected clock and fetch. Revisit if fleet size or version-refresh frequency grows enough that 6 probes/hour/machine matters, or if updates need sub-10-minute staleness detection on git-free machines.

## 2026-07-16 16:17 EDT (-0400) - Bound Replay History With Verified Checkpoints And Deltas

- Problem: Verified temporal replay originally wrote a complete memory and entity snapshot after every durable write. A disposable 40-write baseline took 9.85 seconds and occupied 1,331,200 bytes of generation history versus a 32,768-byte current index (40.6x disk amplification), confirming quadratic history growth. The first delta implementation also exposed volatile serializer timestamps that rewrote every existing row on each generation, preventing useful deltas even when the logical change was one appended record.
- Change: Generation schema v2 stores the best of full, gzip, content-addressed text delta, or gzip delta for each artifact. Deltas bind the exact parent generation, base content hash, and reconstructed result hash; checkpoints are forced before a chain can exceed the configured interval. Agent-memory index rows now use the memory's stable `updatedAt`, and generated entity rows do the same, so unchanged rows remain byte-identical. Reader verification reconstructs chains with memoization and rejects storage, base, manifest, or result tampering. Legacy v1 full snapshots remain readable and can be the base of a v2 generation.
- Retention policy: Agent Memory retains at most 256 generations with a forced checkpoint every 32; full-vault search retains at most 32 with a checkpoint every 4. Pruning occurs only after the new pointer commits and advances to a verified checkpoint, using recoverable tombstone staging plus an atomic `coverage.json` commit. Retention may keep fewer than the maximum to preserve a complete chain. Coverage exposes retained/verified/invalid/checkpoint counts, cumulative pruning, and the earliest complete replay point through list-generations, CLI, and health. Pruning removes generated indexes, not authoritative Markdown notes.
- Benefit: The reproducible real-path 40-write benchmark completed in 1.088 seconds. Thirty-five generations used deltas and five were checkpoints; stored artifact payloads were 44,496 bytes versus 1,026,565 bytes for complete artifact copies (4.33%), and the complete generation directory including manifests was 292,428 bytes. A 300-write run completed in 18.859 seconds, retained 233 verified generations, pruned 67 at safe checkpoints, reported zero invalid generations, and stored 379,361 artifact bytes versus 53,771,336 complete-copy bytes (0.71%). The focused synthetic 40-generation corpus, which uses less-compressible growing data, stored 594,915 bytes versus 1,936,040 complete snapshots (30.7%). These are local disposable-vault measurements, not fleet-wide latency claims.
- Preserved behavior: Every committed write still has a complete logical snapshot, current and retained historical replay stay exact, current/parent/deeper corruption fallback remains available, the current pointer commits last, compatibility JSONL mirrors stay complete, and Markdown remains authoritative. Explicit requests for pruned ids fail instead of silently replaying another generation.
- Tradeoffs: Replay before the recorded coverage boundary is intentionally unavailable after pruning and cannot be reconstructed from Markdown with generation-exact ranking state. Small per-generation manifests and filesystem blocks remain overhead even when artifact deltas are tiny; manifests still carry full source receipts, so retained metadata grows linearly with the current source set under the fixed generation bound. Compression and delta selection require at least 64 bytes and 10% savings, avoiding complexity for negligible wins. Opportunistically efficient full artifacts may create extra checkpoints before the forced interval. Invalid/missing coverage or unexpected lineage gaps pause deletion, so a damaged store can temporarily exceed its bound rather than risk destructive cleanup with an invented replay horizon.
- Files: `src/lib/services/obsidian/brain-index-{artifact-storage,generations}.ts`, Agent Memory and entity serialization, full-vault status, API/CLI/health surfaces, `scripts/test-{brain-index-storage-retention,shared-brain-generations-capsules,hive-brain-memory-hardening}.mjs`, `scripts/benchmark-brain-index-storage.mjs`, Whole Brain/setup/skill contracts, and this ledger.
