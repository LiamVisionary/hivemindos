# Optimizations

This file records performance and latency optimizations that future agents should
reuse before re-debugging the same paths. Keep entries concrete: what was slow,
what changed, which files own the behavior, how it was verified, and what to
watch next.

This complements `CHANGELOG.md`. The changelog is release-facing; this file is
the engineering memory for optimization decisions and performance traps.

## Rules For New Entries

- Add an entry whenever you add, remove, or materially change a performance optimization, cache, timeout, debounce, polling rule, lazy load, prompt-size reduction, or expensive-work deferral.
- Record the measured bottleneck or failure mode, not just the code change.
- Include exact files or areas changed.
- Include verification commands and live timing evidence when available.
- Note tradeoffs, cache freshness, fallback behavior, and when the optimization should be revisited.
- If an optimization affects prompt injection or agent context, state what context is preserved and what is skipped, cached, compacted, or deferred.

## 2026-07-12 11:03 +0800 - Spend The Existing Hive Vault GPU Budget On Visible Neural Tissue

- Problem: The committed full-screen Hive Vault renderer was fast enough at the 160-node cap, but the live route still read as small isolated points over a bright cobalt plane. Only two ambient nearest-neighbor fibers per node, short dendrites, 900 depth motes, and a distant fit camera left too little visible tissue when the real vault graph contained only ten wiki-link edges.
- Change: Ambient webbing now uses three nearest neighbors, dendrites grow longer and fork more often, the depth field uses 1,400 low-cost instanced points, and the camera fits at 1.72× cloud radius instead of 2.05×. The existing 1.75 device-pixel-ratio cap, 160 visible-node cap, instanced soma/halo meshes, shared line buffers, 9,000 pulse-slot ceiling, reduced-motion path, and GPU disposal stay intact. Dark fibers receive more of the available contrast while the shader independently reduces light-theme fiber, pulse, and dust opacity.
- Tradeoff: The renderer builds more line segments and point instances per topology update, and the denser field increases fragment overdraw. The graph remains bounded by the existing node/pulse caps and the extra work is GPU-batched; do not raise node count, pixel ratio, web neighbors, or pulse slots again without profiling an integrated-GPU Tauri build. If frame time regresses, first drop depth motes toward 900 or web neighbors back to two rather than removing real wiki-link bundles or interaction labels.
- Files: `src/features/dashboard/views/BrainSynapseCanvas.tsx` and `src/features/dashboard/views/brain-synapse-gpu.ts`.

## 2026-07-11 20:28 +0800 - Coalesce Collector Skill Inventory Polls

- Problem: The Hermes host has a runaway AEON mirror tree with at least 10,000 `SKILL.md` files. Fleet polling requested `/skills` roughly every 10 seconds, and each request independently walked and summarized the capped tree. The live collector spent about 45% CPU and repeatedly logged the cap warning; its earlier restart reported a 3.2 GB peak.
- Change: Summary-only skill inventory requests share one in-flight scan and reuse the result for 60 seconds. `?refresh=1`, auto-sync change processing, and source-file exports intentionally bypass the cached summary. The cache is in-memory and resets when the collector restarts.

- Tradeoff: Ordinary polling can show a newly installed skill up to 60 seconds late. UI actions that require immediate freshness should request `refresh=1`; change-driven auto-sync already forces a fresh scan. The runaway mirror directory still needs a reviewed cleanup—the cache contains its cost but does not delete user files or repair the underlying tree.
- Files: `scripts/agent-telemetry-collector.mjs`, `scripts/lib/async-ttl-cache.mjs`, and the live collector regression in `scripts/test-chat-maintenance-safety.mjs`.

## 2026-07-10 19:41 +0800 - Serialize xAI OAuth Rotation Without Adding Inference Latency

- Problem: xAI refresh tokens rotate and are single-use, but HivemindOS copied one grant into the fleet-synced shared env and multiple Hermes auth stores. HivemindOS and Hermes then refreshed independently, so the first winner invalidated every stale copy; the live result was an expired access token plus `invalid_grant: Refresh token has been revoked`, forcing a manual reconnect despite OAuth supporting automatic renewal.
- Change: HivemindOS now owns its normal session under `~/.hivemindos/oauth/xai.json` with `xai.lock`; it has no Hermes dependency. A small broker re-reads state after acquiring that cross-process lock, refreshes once, atomically writes the rotated pair, and lets waiting callers adopt it. An existing Hermes login remains optional: one local, non-secret authority selector references its `auth.json` in place, and the same broker then uses Hermes' `auth.lock` without copying the refresh token. HivemindOS no longer performs an independent refresh or writes rotating xAI tokens to shared env. Legacy env copies migrate once into the native store and are retired. The app caches a valid access token in-process and coalesces same-process refresh promises, so ordinary inference bypasses both Python startup and network refresh.
- Preserved behavior: xAI login remains app-owned PKCE in the system browser, the public client/scopes and direct xAI inference endpoint are unchanged, Agent Settings still recognizes an existing Hermes login, and model/tool/prompt-cache routing is unchanged. Users of native HivemindOS, Codex, Claude, AEON, OpenClaw, or future runtimes use the HivemindOS-owned OAuth path; runtime choice does not create a Hermes requirement. Secrets still travel only through process stdin/local owner-only files and never enter browser status responses or logs.
- Tradeoff: OAuth is now a machine-local session, not a fleet-replicated secret. Each machine that directly uses xAI OAuth needs its own login unless a future centralized credential broker is intentionally designed. The first token resolution after an app process start pays one local broker spawn; repeated inference uses the in-memory access token until the 60-second refresh window. An independently managed Hermes login can remain a separate authority, but HivemindOS never duplicates its rotating token. A grant revoked before this change cannot be recovered and needs one clean reconnect.
- Files: `scripts/xai-oauth-token-broker`, `src/lib/services/{xai-oauth-token-store,xai-oauth,hive-env-write,hive-env-command}.ts`, xAI OAuth route, embedded Tauri runtime packaging, and focused tests.
- Verification: The regression launches two broker processes in a disposable home with no Hermes installation, observes one refresh HTTP request, one rotated native token pair, and matching access results for both callers, then proves a revoked grant is quarantined after one failed refresh and later requests fail locally without another HTTP call. The real app accessor is exercised once against that native store and once against a separately selected disposable Hermes profile, proving both authority paths without copying or rotating the Hermes refresh token. Focused setup/routing tests and lint pass. Before the ownership correction, the live status route read the revoked state correctly and Queen skipped it through its configured provider fallback in 1.59 seconds; live automatic refresh against xAI remains intentionally pending until the user reconnects because the current grant is terminally revoked.
- Watch next: After reconnect, force one expiry-window refresh and verify the access/refresh pair rotates once in native `xai.json`, a second simultaneous request reuses it, and Queen inference proceeds without a reconnect prompt. If the one-time process-start broker cost becomes measurable, keep the lock authority intact and optimize broker residency rather than duplicating refresh ownership again.
