# Optimizations

This file records performance and latency optimizations that future agents should
reuse before re-debugging the same paths. Keep entries concrete: what was slow,
what changed, which files own the behavior, how it was verified, and what to
watch next.

This complements `CHANGELOG.md`. The changelog is release-facing; this file is
the engineering memory for optimization decisions and performance traps.

## Rules For New Entries

- Add an entry whenever you add, remove, or materially change a performance optimization, cache, timeout, debounce, polling rule, lazy load, prompt-size reduction, or expensive-work deferral.
- Record the measured bottleneck or failure mode, not just the code change.
- Include exact files or areas changed.
- Include verification commands and live timing evidence when available.
- Note tradeoffs, cache freshness, fallback behavior, and when the optimization should be revisited.
- If an optimization affects prompt injection or agent context, state what context is preserved and what is skipped, cached, compacted, or deferred.

## 2026-07-04 - Move dashboard-state Tauri invokes off the UI-process main thread + cap persisted fleet snapshots

- Problem: `pnpm tauri:dev` had a visible click-to-response delay on every interaction (frames of 130–200ms, occasional 4–8s stalls), while the same dashboard in Chrome and the packaged build were fast. Machine contention, window transparency, CSS paint effects, and React re-renders were all chased and disproven on-device. Root cause found via `sample` of the live app: `wry` delivers synchronous `#[tauri::command]` invokes — and serializes their responses — on the UI-process main thread. `dashboard_state_write` fires on nearly every interaction and every fleet-snapshot poll, and it read+parsed+cloned+rewrote a 33.5 MB `~/.hivemindos/dashboard-state.json`, then serialized the entire store *again* as an unused IPC response, in an `opt-level=0` debug binary. A light 10s probe caught 904/7,476 main-thread samples inside `serde_json`; WKWebView input and layer-tree commits queue behind that same thread. The 33 MB store was itself a leak: `hivemindos.fleetSnapshots.v1` held 2,822 never-evicted ephemeral per-PID hermes agents (30.6 MB) because the snapshot merge only ever adds.
- Change: (1) `compactFleetSnapshotsForPersist` caps *persisted* fleet snapshots to the 128 most-recently-checked agents (in-session map stays complete); the store self-healed 33.5 MB → 1.7 MB on the first persist. (2) `dashboard_state_read`/`dashboard_state_write` are now `async` so they run on the tokio runtime instead of the main thread, and the write response was slimmed to `{ ok, updatedAt }` (the only caller reads `ok`). (3) `[profile.dev.package."*"] opt-level = 2` optimizes dependencies (serde_json/tauri/wry) in dev while keeping the app crate unoptimized for fast iteration.
- Preserved behavior: The full fleet-snapshot map is unchanged in memory; only the persisted seed is capped. Native read/write semantics (atomic temp-file rename, per-key merge, write lock) are unchanged. Browser/HTTP path (`/api/dashboard/state`) is untouched.
- Tradeoff: A cold boot rehydrates at most 128 persisted fleet snapshots instead of all historical ones — acceptable because live discovery repopulates the map and the persisted set was mostly dead per-PID agents. The `opt-level=2` dep profile adds a one-time dependency rebuild, then caches.
- Files: `src/features/dashboard/dashboard-storage.ts`, `src/features/dashboard/DashboardApp.tsx`, `src-tauri/src/dashboard_state.rs`, `src-tauri/Cargo.toml`, `CHANGELOG.md`, `OPTIMIZATIONS.md`, `PERFORMANCE_GOTCHAS.md`.
- Verification: `sample` of the pre-fix app during interaction showed 904/7,476 main-thread `serde_json` frames; after rebuild+relaunch, a matched interaction `sample` that actually fired a persist (13 `dashboard_state` frames present) showed those frames on `tokio-rt-worker` threads and 0 `serde_json`/`dashboard_state` frames on the main thread (parked in kernel waits). Store self-healed 33.5 MB → 1.7 MB (fleetSnapshots 30.6 MB → 739 KB, exactly 128 agents). `pnpm exec eslint src/features/dashboard/dashboard-storage.ts` clean; `pnpm test` gate 89/90 (only the pre-existing `check-sizes` red on other sessions' files; DashboardApp.tsx dropped back under its allowance).
- Watch next: If desktop lag returns, `sample` the app PID during interaction and check whether an invoke handler (`serde_json`, project Rust, or `tauri::ipc` frames) is on the main thread before theorizing about paint/transparency/React. Keep any new `#[tauri::command]` tiny or `async`, and never echo large state in an invoke response. See `PERFORMANCE_GOTCHAS.md` §G1 for the full trap and diagnosis recipe.

## 2026-07-01 23:10 +0800 - Bound Stripe Checkout Credit Polling

- Problem: After a card-funded HivemindOS Models checkout, the desktop app had no automatic way to notice the Stripe webhook-minted credit balance. Users had to press Refresh, and even then the modal-local balance could update without persisting the balance that provider cards read.
- Change: The guided HivemindOS Models setup starts a bounded credit-balance watcher after card checkout opens or after the `hivemindos://models/credits` desktop return event arrives. It waits 2.5 seconds before the first poll, then checks every 5 seconds, and stops after 10 minutes, when credits are funded, or when checkout is canceled. Each successful balance read persists the hosted credit balance back onto the agent profile.
- Preserved behavior: Manual Refresh remains available and uses the same balance persistence path. Stripe webhooks remain the authority for credit minting; polling only reads the local hosted-credit balance endpoint and never grants credits by itself.
- Tradeoff: The modal may make up to about 120 lightweight balance reads during a long pending checkout. That is intentional because checkout completion is user-visible and bounded to one active setup flow. Revisit if Stripe webhook latency routinely exceeds 10 minutes or if multiple concurrent setup modals become common.
- Files: `src/features/dashboard/views/chat/GuidedHivemindosModelsSetup.tsx`, `src/app/api/hivemindos/models/credits/route.ts`, `src/lib/services/paid-agent-cloud-client.ts`, `src-tauri/src/desktop_navigation.rs`, `src-tauri/tauri.conf.json`, `OPTIMIZATIONS.md`.
- Verification: Passed `node scripts/test-wallet-paid-models.mjs`, focused ESLint for the touched HivemindOS Models checkout files, focused `git diff --check`, `cargo check --manifest-path src-tauri/Cargo.toml`, private Worker `pnpm typecheck`, and a filtered TypeScript scan with no diagnostics for the touched public files.

## 2026-06-29 00:34 +0800 - Keep Large Source Notes In Shared Brain Recall

- Problem: Full-vault recall could become noisy for broad queries because large imported source notes over 256 KiB were excluded from both the generated lexical index and local fallback reads. The live vault reproduced this with `Memory/Imported Sources/Bankr Platform Documentation.md`, about 546 KB: the old generated index did not contain it, so a targeted Bankr documentation query ranked unrelated imported agent memory above the intended source and the live benchmark scored 6/7 Top-1.
- Change: Full-vault indexing and fallback reads now cap markdown at 1 MiB instead of 256 KiB. Generated full-vault index rows include `indexedByteLimit`, and readers reject rows generated with a different cap so stale generated indexes rebuild after the cap changes. Full-vault ranking now adds a distinct query-term coverage score, including a small penalty for matching less than half of a multi-term query, so repeated partial keyword hits are less likely to outrank a note that covers the full intent. The `hive-brain` CLI and shared-brain quality benchmark use the same cap/metadata/coverage contract, and `scripts/test-hive-brain-recall-quality.mjs` adds an Evo-compatible actual-CLI harness with eight recall tasks and trace output, including a broad-search keyword-spam adversary.
- Preserved behavior: The generated full-vault lexical index remains the first recall path, followed by ripgrep, grep, and bounded filesystem reads. The larger cap only expands eligible markdown bodies; skip rules, scoring, automation transcript guards, and typed Agent Memory behavior remain unchanged.
- Tradeoff: First rebuild after the cap change can take longer, and the generated index can grow when the vault has large source notes. The cap is still bounded at 1 MiB to avoid letting oversized documents dominate memory and rebuild time. Coverage scoring intentionally favors fuller lexical intent matches, which can demote a short note that is semantically relevant but uses fewer query words. Revisit if important source notes exceed 1 MiB, if rebuilds become slow, or if recall starts needing chunk-level scoring or semantic reranking instead of whole-note lexical scoring.
- Files: `src/lib/services/obsidian/full-vault-search-index.ts`, `src/lib/services/obsidian/agent-memory/core.ts`, `scripts/hive-brain`, `scripts/benchmark-shared-brain-search-quality.mjs`, `scripts/test-hive-brain-recall-quality.mjs`, `CHANGELOG.md`, `OPTIMIZATIONS.md`.
- Verification: Live vault baseline before the change was 6/7 Top-1; after index refresh it is 7/7 Top-1. Latest live run of `node scripts/benchmark-shared-brain-search-quality.mjs --vault /Users/liam/Documents/Obsidian/hivemindos-vault --json` measured indexed median about 10.79 ms versus old-search median about 505.65 ms, roughly 46.86x faster. Direct `hive-brain recall` now ranks the Bankr source note first. Passed `node scripts/test-hive-brain-recall-quality.mjs --min-score 1`, Evo-format result/traces output, `pnpm benchmark:shared-brain-search` with 8/8 Top-1 on the fixture and indexed median about 0.28 ms, `evo run exp_0002 --check`, `evo gate check exp_0002`, and `evo run exp_0002` with score 1.0 across eight tasks.
- Watch next: If "too noisy" appears again, inspect whether the expected note is present in `Operations/Brain Services/Full Vault Search Index.jsonl` with the current `indexedByteLimit` before tuning ranking. If rank quality remains weak after coverage is confirmed, the next likely improvement is chunked BM25 or hybrid semantic reranking rather than another broad full-vault scan.

Embeddings are deferred. Retrieval telemetry only nudges order; it never filters out low-usage or new memories.
